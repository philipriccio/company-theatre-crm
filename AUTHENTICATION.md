# Personal CRM accounts — staged October 31, 2026

**Local candidate only. No deployment, live account enrollment, production database change, proxy change or email send.** Baseline a5e7ba8 is the October 24 website-signup-label release, including October 22 security patches. Existing production Basic authentication is unchanged.

## User workflow

Sign in using a personal email/password, then Settings → Your account → Change password. Enter current password, new password and confirmation. Password managers, paste, spaces and Unicode work; 15–128 Unicode codepoints (NFC-normalized), no mandatory composition or routine expiry. Password change rotates this browser session and revokes all prior sessions atomically. Failed validation keeps form input. Logout revokes the server session, not just the cookie. Accounts have seven-day absolute sessions, no disruptive short idle logout, and can be disabled centrally. All current human accounts have the same existing CRM capabilities; roles are not invented here.

The offline denylist contains 96,517 unique common passwords from a pinned MIT-licensed SecLists corpus plus CRM-specific defaults. Provenance, source SHA256, attribution/license and a reviewed-local-file update utility are in security/ and scripts/update-password-denylist.ts. Runtime never transmits passwords or downloads lists. This improves coverage, not a guarantee against every historical breach.

## Security boundary

- Default-deny Node proxy covers all paths, including extension-like paths and future API routes. Every existing private API also calls the shared guard directly; public exemptions apply only to the proxy, never these private guards. Admin layout/account page validate sessions independently.
- Passwords use salted scrypt N=32768/r=8/p=3, 64-byte key. Tokens use 256-bit random entropy; only SHA-256 token digests persist. Seven-day cookies are HttpOnly, SameSite=Lax, Path=/, and Secure with `__Host-` prefix on HTTPS. The non-Secure local cookie is permitted only for explicitly configured loopback HTTP origins.
- `CRM_AUTH_ORIGIN` is required and exact (no trailing slash). Production requires HTTPS. Incoming proxy username headers are never identity. No shared-account fallback, registration, public reset endpoint or automatic email is introduced.
- All unsafe browser-session requests and login/logout require exact configured Origin, reject cross/same-site Fetch Metadata, and fail closed on missing configuration/database availability. Authentication JSON reads are capped at 8 KiB and five seconds. Existing signed public handlers retain their own validation, limits and capabilities.
- Public exceptions are exact methods/paths: GET/HEAD login/static favicon/assets, signed unsubscribe page and tracking; POST signed webhooks, website signup and scratch intake, login; GET/POST unsubscribe API. No directory-wide API exemption. Public handler code is unchanged.
- Database-backed fixed-window throttling: eight login attempts/account and 120 globally per 15 minutes; eight password-change attempts/user per 15 minutes. No untrusted forwarded-IP limiter. Throttles intentionally do not reset on success. This trades bounded denial-of-service susceptibility for an enforceable small-team ceiling; production edge rate limits and alerting remain desirable.
- User row locking serializes login and password change; change rechecks active session under lock, deletes all previous sessions, then issues one new token in the same transaction. A lost successful response can require signing in with the new password; the form says so.
- Login success/failure, password-change success/failure, logout, access denial, first throttle block, operator recovery/revocation and machine authorization/scope denial are audited without passwords/tokens. Unknown-user failure subjects are hashed. Anonymous denial audit volume is capped at60 records/15min with a throttle-block summary; enforcement continues. Auth housekeeping removes at most1000 expired sessions and1000 throttle rows expired over24h per run; never audit history. npm run auth:housekeeping is available for reviewed daily scheduling. Machine authorization events record admitted attempts, not a claim that the downstream business action succeeded.
- Legacy state-changing GET `/api/cron/send-scheduled` now returns405; authenticated same-origin POST is the replacement. There is no inferred scheduler approval or machine bypass. Send approval persistence now uses authenticated name/email/ID, not user-supplied `approvalName`; the existing explicit confirmation UI remains.
- CSP intentionally not added blindly: campaign preview/copy editor have existing sandbox/frame requirements. Existing email behavior, delivery-disabled configuration and recipient data are untouched.

## Private operator transport (local engineering proof only)

`scripts/auth-operator/relay.mjs` is a dependency-free Node host relay for the explicit operator container. It accepts only a full immutable container ID and its nonsecret operator port. Run on the Docker host using `node scripts/auth-operator/relay.mjs FULL_CONTAINER_ID OPERATOR_PORT`; the CLI binds **127.0.0.1 at that same port**, never a public interface. Per browser connection it spawns `docker exec -i` with a constant Node stdin/stdout-to-container-loopback bridge. No credentials, payload logging, shell interpolation, Docker port publishing, or request/header rewriting is used. Docker stderr is discarded to avoid unexpected diagnostic disclosure; connection failure is visible as a closed browser request, not success. Inspect target metadata in the private operator UI before submitting.

From the trusted administrator device, use an SSH local forward binding 127.0.0.1 at the **same operator port** to host 127.0.0.1 at that port. Matching ports preserve the operator's exact Host/Origin checks. Port collision fails closed; do not work around it by public binding or relaxed Host checks. This requires two distinct network namespaces; ordinary container-IP forwarding cannot reach its loopback listener.

Bounds: 8 concurrent connections; 1 MiB each direction per connection; 10-second idle timeout; 30-second absolute connection timeout; 15-minute host relay lifetime. Operator HTTP retains its 8 KiB/5-second form bounds. Stop with SIGINT/SIGTERM; the relay closes all sockets and terminates local Docker-exec clients, escalating after one second. A detached container bridge independently exits within 30 seconds even if Docker-client termination does not kill it. **Stop/remove the operator container separately immediately after use**; relay expiry does not stop the container. A remote operation whose response was lost may already have committed; verify metadata/state before retrying.

Local tests exercise actual child pipes/TCP, large-response integrity, caps, failures/cleanup, and real operator Host/Origin/body rejection with a limited database role. Docker is unavailable on the local host: real Docker/SSH namespaces, private protected connection injection and production enrollment are **not verified**. No machine credential-store broker is implemented by this relay; it transports the operator form only.
